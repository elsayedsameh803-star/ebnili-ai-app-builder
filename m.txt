fix(auth): make the OAuth cookies reliable in a fresh/incognito session

Step B of the sign-in investigation (Google/GitHub failed only in a fresh
session, while an existing session short-circuited the whole flow).

B1 — cookie set/clear now share one attribute set. The state and PKCE
cookies were created with `secure: true` in production but deleted with a bare
`{ path: "/" }`. A cookie can only be replaced when the deletion repeats the
same name/domain/path/Secure attributes, so on some browsers the single-use
delete silently did nothing and a stale nonce survived the round trip — which
is exactly the "works in a normal profile, breaks in a fresh one" signature,
because an existing session never exercises the callback at all. One
`authCookieOptions()` / `clearAuthCookie()` pair is now used by every set AND
every clear (including logout, which also clears the PKCE cookie now).

B2 — `/api/auth/providers` is the single source of truth. It now returns the
base URL, which route will actually handle the handshake ("supabase" or
"direct") and the exact callback that has to be whitelisted. The client used
to read the button list from this endpoint and the callback URLs from
`/api/auth/config`, so the two could describe different things; the UI now
derives everything from one response, which also means the error screen shows
the genuinely correct URL to copy when a redirect_uri is rejected.

No Gemini code and no API key were touched. Desktop UI unchanged.
TypeScript clean, build clean (1704 modules), deployed with --prod --force
and verified live: /api/auth/providers returns route "supabase" and the
callback base.
